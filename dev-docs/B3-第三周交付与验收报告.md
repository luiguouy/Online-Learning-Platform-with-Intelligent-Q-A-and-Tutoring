## 三、逐条验收证据

### B3.1 边界与异常测试

**缺陷清单（修复前 → 修复后）**：B3.1 实测暴露 **5 类真实缺陷**，全部会在旧代码下返回 HTTP 500，均已修复为友好业务码。

| # | 触发条件 | 修复前 | 修复后 | 修复位置 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 路径/查询参数类型不匹配（`courseId=abc`） | 500 | `400 参数格式不正确：courseId` | `GlobalExceptionHandler` |
| 2 | 请求体 JSON 字段类型错（`status:"x"`） | 500 | `400 请求体格式不正确，请检查字段类型` | `GlobalExceptionHandler` |
| 3 | 文件名超长（299 字符 > 200 上限） | 500（`FileNotFoundException`） | `400 文件名过长（最多 200 个字符），请重命名后重试` | `TeacherDocumentController` |
| 4 | **SSE 空/纯空白提问** | **HTTP 500 空体** | `event:error {"errorCode":4000,"message":"提问内容不能为空"}` | `SseChatController` |
| 5 | 请求路径不存在（拼错接口 / 静态资源） | 500 | `404 请求的接口或资源不存在：/xxx` | `GlobalExceptionHandler` |

> **缺陷 4 的根因值得单独说明**：`/api/qa/chat/stream` 声明 `produces=text/event-stream`，而 `@RestControllerAdvice` 返回的是 JSON `Result`。前端 `EventSource` 发送 `Accept: text/event-stream`，Spring 内容协商找不到可写介质 → `HttpMediaTypeNotAcceptableException` → Tomcat 兜底 **HTTP 500 空体**，前端只能看到"连接失败"、没有任何原因。正确做法是**不再走异常体系**，直接在 Controller 里通过 `emitter.send(SseEmitter.event().name("error")...)` 下发 `event:error` 事件——本次已改用该方案。

**独立复核（不依赖验收脚本，直接读原始响应）**：
```
【参数类型】GET /api/qa/sessions?courseId=abc              → HTTP=200 code=400 "参数格式不正确：courseId"
【参数类型】GET /api/teacher/qa/records?courseId=abc&…      → HTTP=200 code=400 "参数格式不正确：courseId"
【请求体】  POST /api/qa/records/1/feedback status="x"      → HTTP=200 code=400 "请求体格式不正确，请检查字段类型"
【路径】    GET /api/does-not-exist                        → HTTP=200 code=404 "请求的接口或资源不存在：/api/does-not-exist"
【路径】    GET /robots.txt                                → HTTP=200 code=404 "请求的接口或资源不存在：/robots.txt"
【文件名】  upload 299 字符文件名                           → HTTP=200 code=400 "文件名过长（最多 200 个字符）…"
【大文件】  upload 51MB                                     → HTTP=200 code=400 "文件超过 50MB 上限，请压缩后重试"
【空提问】  question=""                                     → HTTP=200 events=[event:error] {"errorCode":4000,"message":"提问内容不能为空"}
【空白提问】question="   " / "\t\n  \r\n"                   → HTTP=200 events=[event:error] {"errorCode":4000,...}
```
全部为 **HTTP 200 + 业务码**，符合统一契约；无一处 500。

> **上传口径补充（Issue #46 裁决后）**：上表 `51MB → 400` 命中的是 **multipart 传输层 50MB 容器粗保护**；**业务口径是 20MB**（`rag.ingest.max-file-bytes` 解析层）—— 即 **21~50MB 的课件会通过 multipart、但在解析层落 `FAILED`** 并在 `errorMsg` 说明原因。两者分层，权威表述见 `MEMBER_D_DEV_GUIDE.md` 的「上传大小口径说明」。

**提问长度三区间边界语义（原始 socket 二分实测；2026-09-30 复测修正，见 §四.1）**：

| 字数（中文） | 结果 |
| ---: | :--- |
| 1 ~ 1600 | ✅ 放行出流（`references → message → done`） |
| 1601 ~ 7259 | ✅ 业务拦截 `event:error {errorCode:4000}` |
| ≥ 7260 | ⚠️ 协议层 **HTTP 400**（请求头块 65537 字节 > 上限 65536，**进不到 Controller**） |

- 业务上限 `MAX_QUESTION_LENGTH = 1600` 含端点：1600 放行、1601 拦截。
- 协议层上限 = `server.max-http-request-header-size` 的字节值（**1:1**）：配 `64KB` 时为 65536 字节
  （7259 字 / 65528 B 通过，7260 字 / 65537 B 被拒，HTTP 400）；不配该项（Spring Boot 默认 8KB）时为 8192 字节
  （888 字 / 8189 B 通过，889 字 / 8198 B 被拒，HTTP 400）。
- 故 1600 字（≈14400 字节）仅占 64KB 预算的 **22%**，业务上限对协议层有巨大余量。
- ⚠️ **给成员 C 的提示**：前端提问框 `maxlength=1600` 已落地，其定位是**产品级输入约束**（避免超长提问浪费检索与模型开销），
  而**不是**"防止请求被容器拒掉"的必需品——在 64KB 配置下直到 7260 字才会触发协议层拒绝。

**B3.1 汇总**：`PASS 46 / FAIL 0`。

## 四、随本次修正的两处"回头账"（重要）

验收中发现两周前的一处**误判**，本次一并纠正：

1. **`server.max-http-request-header-size` 必须保留；其上限"恰好等于配置值"**。

   本条经历两轮修正，最终以**原始 socket 二分 + 精确记账**（排除 HTTP 客户端库改写请求的干扰）定案：

| 配置 | 实测上限（计数口径 = 请求行 + 所有请求头 + 各行 CRLF + 结束空行） | 该配置下中文提问的临界字数 |
| :--- | :--- | :--- |
| 不配（Spring Boot 默认 8KB） | **8192 字节**（填充头 8068 B 通过 / 8069 B 拒绝） | 888 字通过 / **889 字 HTTP 400** |
| `max-http-request-header-size: 64KB` | **65536 字节**（填充头 65412 B 通过 / 65413 B 拒绝） | 7259 字通过 / **7260 字 HTTP 400** |

   - **结论 1**：上限**恰好等于配置值（1:1）**。本报告早期版本写的「≈8056 字节 / ≈16370 字节」「约为配置值的 1/4」是**测量口径错误**（把"请求行"与"请求行 + 请求头"混为一谈，且未做精确记账），**已作废**。
   - **结论 2**：超限返回 **HTTP 400**，不是 431（早期版本记的 431 亦作废）。
   - **结论 3**：该项**是前提而非可选**。删掉它，上限掉回 8192 字节，中文提问在 **889 字**即被容器拒掉（HTTP 400），低于业务上限 1600 字——"超长提问走 `event:error` 友好返回"这条保障会退化成"请求进不到 Controller 的无信息失败"。故**与 `MAX_QUESTION_LENGTH` 配套，不可单独删改**。
   - 复现脚本：`.workbuddy/tools/probe_header_limit.py`（通用上限二分）、`.workbuddy/tools/probe_sse_charset_coupling.py`（SSE 端点临界字数）—— 均为**本机脚本、未入库**。
     > ⚠️ **证据链说明**（PR #61 审查 P2-6）：`.workbuddy/` 已被 `.gitignore` 忽略，这两个脚本是**本地产物、未随仓库入库**，CI 与其他成员无法直接运行。**他人等价路径** = 下面这句所述口径（**不必**拿到脚本）。**本报告的数据以本节表格与 §四.1 的口径为准**；若需重跑，按"原始 socket 发 `Accept: text/event-stream` 请求 + 定长中文提问 + 二分"的口径自行采集即可（脚本逻辑简单，核心是绕开 HTTP 客户端库的自动重试/改写）。

2. `week2_full_accept.py` 中"落库 filePath 为绝对路径"的断言已过期：A 加 `@JsonIgnore` 后该字段**不再出现在响应里**。已把断言改成"响应不含 `filePath` 键"（这才是修复后的正确契约），字段落库仍由 B3.3 建库脚本与上传链路覆盖。

4. **`feedback` 无"取消评价"语义**：接口只接受 ±1，复位需 SQL。验收脚本已内置清理提示。
5. **技术债（不阻塞冻结）**：`errorMsg` 回传服务器路径、`isDeleted` 下发。
