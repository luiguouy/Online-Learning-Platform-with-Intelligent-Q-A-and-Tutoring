# 团队协作与工程治理规范
> **本文件定位**：`DEV_SPECIFICATION.md` 管"代码怎么写"，本文件管"**人怎么一起干活**"。两者冲突时以 `DEV_SPECIFICATION.md` 第四章接口契约为准。
> **落地原则（轻量优先）**：只用 **GitHub 原生能力**（Issues / Pull Requests / Actions / Projects）+ 一个群，不引入 Jira、Confluence、飞书多维表格等重型工具。4 人团队引入重工具的维护成本高于收益。
> **读者**：全员必读（尤其是组长与每次发起 PR 的人）。

---

## 一、 角色与决策权（RACI 矩阵）

分工文档定义了"谁做什么"，本节定义"**谁说了算**"——企业级协作与作业小组的核心区别不在于分工表，而在于**决策权清晰**。

**R / A / C / I 含义**：R=负责执行，A=最终批准并担责，C=决策前需咨询，I=决策后需知会。

| 决策事项 | R 执行 | A 批准 | C 需咨询 | I 需知会 |
| :--- | :--- | :--- | :--- | :--- |
| 技术选型与架构变更 | 成员 A | 成员 A（组长） | 成员 B | 全体 |
| 接口契约新增 / 变更 | 接口提供方 | 成员 A | 接口调用方 | 全体 |
| 数据库表结构变更 | 成员 B | 成员 A | 成员 A（RAG 侧需确认） | 成员 C/D |
| SSE 协议字段 | 成员 A | 成员 A | 成员 C | 全体 |
| 前端 UI / 交互细节 | 成员 C / D | 成员 A | — | 全体 |
| 分支合并到 `dev` | 提交者 | 成员 A | — | 全体 |
| 分支合并到 `main`（发布） | 成员 A | 成员 A | 全体 | 全体 |
| 密钥与本地配置管理 | 各自 | 成员 A | — | — |
| 演示与答辩安排 | 成员 D | 成员 A | 全体 | — |

**决策规则（避免扯皮与拖延）**：
1. **咨询是义务的**：A 列在做决定前必须完成 C 列咨询，跳过咨询的批准无效。
2. **分歧 24 小时规则**：相关方讨论超过 24 小时未达成一致，由 **A 列（组长）直接拍板**，并在对应 Issue 里用 3 句话记录"决策是什么、为什么、牺牲了什么"。拍板后全员执行，不再争论。
3. **沉默视为同意**：@ 到本人且 24 小时内未回复，视为无异议。
4. **决策留痕**：所有影响接口、表结构、依赖的决策，结论必须写进 Issue 或 PR 描述，禁止仅存在于群聊记录里——群聊会刷屏消失，Issue 不会。

## 二、 分支策略与保护规则

### 2.1 分支模型（沿用 `DEV_SPECIFICATION.md` 1.1，此处补充命名细则）

```text
main            ← 演示/发布分支，永远可运行，只有组长能合并
└── dev         ← 日常集成分支，所有 PR 的目标分支
    ├── feature/A-rag-ingest      ← 成员字母 + 短横线 + 功能名
    ├── feature/B-qa-record
    ├── feature/C-sse-chat
    ├── feature/D-teacher-board
    └── fix/B-login-403           ← 修复分支同样带成员字母
```

**命名强制格式**：`feature/<成员字母>-<小写英文短名>` 或 `fix/<成员字母>-<小写英文短名>`。
禁止 `feature/xxx`、`feature/test`、`feature/新建文件夹` 这类无法追溯归属的命名——组长在 Review 时看到无主分支应直接要求改名。

### 2.2 分支保护规则（组长在 GitHub 上一次性配置，必做）

路径：`Settings → Branches → Add branch ruleset`（或 Add rule）

| 分支 | 保护项 | 目的 |
| :--- | :--- | :--- |
| `main` | 禁止直接 push；需 1 个 PR；需 1 人 approve；CI 全绿才允许合并；禁止 force push | 演示分支永不污染 |
| `dev` | 禁止直接 push；需 1 个 PR；需 1 人 approve；CI 全绿才允许合并；禁止 force push | 集成分支可追溯，与 3.4 合并条件一致 |

**可选项（推荐）**：配置 `.github/CODEOWNERS` 自动指定 Reviewer：

```text
# 放在仓库根目录（.github/CODEOWNERS）
*                          @luiguouy          # 组长默认 Reviewer
/backend/src/main/java/com/smartqa/platform/service/rag/  @luiguouy  # RAG 核心模块需组长审
```

### 2.3 分支生命周期（防止"长命分支"引发大规模冲突）

- **单个分支存活不超过 3 天**。超过 3 天说明任务拆得不够细——拆小重开分支，而不是硬撑。
- **每日开工前先同步**：`git checkout dev && git pull origin dev && git checkout - && git merge dev`（或 rebase）。
- **合并后立刻删除远程分支**，避免分支列表膨胀成垃圾场。

## 三、 Pull Request 与 Code Review

### 3.1 PR 规模纪律

- **单个 PR 建议 ≤ 400 行改动**（不含自动生成文件）。超过请拆分成多个 PR 或在描述中说明原因。
- **一个 PR 只做一件事**：不要在同一个 PR 里既改 Bug 又重构又调格式——Reviewer 无法有效审查，出问题也无法精准回滚。

### 3.2 PR 描述模板（仓库已配置 `.github/PULL_REQUEST_TEMPLATE.md`，自动填充）

四段式，缺任一段 Reviewer 可打回：

```text
1. 做了什么：一句话说明本次改动
2. 为什么：关联的 Issue（如 Closes #12）
3. 怎么验证：本地跑通的具体步骤与结果（贴编译/运行成功输出，不要只写"已测试"）
4. 影响面：是否改了接口字段 / 表结构 / 依赖？是否影响其他成员？（有则 @ 对方）
```

### 3.3 Review 检查清单（Reviewer 逐条过，不要只点 Approve）

**通用**
- [ ] CI 全绿（有红叉直接打回，不接受"本地能跑"）
- [ ] 无密钥、无 `application-local.yml`、无大文件混入
- [ ] 提交信息符合 Conventional Commits，无 "update / 111 / 修改代码"
- [ ] 改动范围与 PR 描述一致，没有夹带无关修改

**后端（A/B 互审，组长终审）**
- [ ] Controller 不写业务逻辑，Service 不拼 `HttpServletResponse`
- [ ] 所有 REST 接口返回 `Result<T>` 统一包装（唯一例外：鉴权/限流拦截器在 `preHandle` 直写 401/429 JSON，见 `MEMBER_B_DEV_GUIDE.md` 4.6 与 README 铁律 4）
- [ ] 新增接口的字段与 `DEV_SPECIFICATION.md` 4.2 契约一致
- [ ] 数据库变更同步更新了 DDL 脚本
- [ ] SSE 相关改动未破坏 4 事件 JSON 载荷约定，`done` 仍含 `recordId`

**前端（C/D 互审）**
- [ ] 无 `any` 泛滥、无未处理的 Promise（控制台无报错）
- [ ] Token 存 `localStorage` 的键名统一为 `satoken`；请求头统一为 `Authorization: Bearer <token>`（**头值必须带 `Bearer ` 前缀**）
- [ ] SSE 解析按 JSON 处理，未假设裸文本
- [ ] 有加载态 / 空状态 / 错误态，不是只有成功路径

**Review 响应时限（SLA）**：Reviewer 需在 **24 小时内**首次响应（approve 或提出修改意见）。超时未响应，提交者可直接 @ 组长处理。

### 3.4 合并条件（三条同时满足）

1. CI 全绿；2. 至少 1 人 Approve；3. 所有 Review 评论已解决或已回复。

**绝对禁止**：`--no-verify`、`--force` 推送公共分支、为了让 CI 变绿而注释掉失败用例。CI 红的时候修代码，不修流水线（除非流水线本身写错）。

## 四、 持续集成（CI）

### 4.1 门禁矩阵

| 阶段 | 后端 | 前端 | 说明 |
| :--- | :--- | :--- | :--- |
| 密钥扫描 | 正则扫描 `sk-` / `AKIA` / 明文密码 | 同左 | **防 Key 泄露，硬门禁**，最先跑 |
| 编译 | `mvn -B compile -DskipTests` | `vue-tsc --noEmit` + `vite build` | 语法/类型错误零容忍；**本期不要求单元测试**（3 周工期下测试用例已裁剪，门禁以"能编译能构建"为准） |
| 文档/格式 | — | — | 暂不做强制（避免过度工程） |

### 4.2 工作流文件
 
 工作流文件位于仓库根目录 `.github/workflows/ci.yml`。
 该文件已配置 `paths` 过滤器：**push 到 `main`/`dev` 时**，只改了 `dev-docs/` 等纯文档不会触发后端/前端构建。注意 `pull_request` 触发器**没有** `paths` 过滤——任何 PR 都会完整跑一遍门禁（这是有意的：PR 是合并前唯一的全量校验点）。

### 4.3 CI 纪律

- **红叉不过夜**：CI 失败的责任人当天修完；`dev` 分支持续红叉会阻塞所有人，属于 P0 级问题。
- **先本地后远程**：提交前本地先跑一次编译，不要把 GitHub 当免费编译器。
- **禁止绕过**：任何形式的 skip CI 需组长在 PR 中书面同意。

## 五、 完成的定义（Definition of Done）

**"我写完了"不等于"完成了"。** 一个任务只有同时满足以下 5 层，才算 Done，才允许发起 PR：

| 层级 | 完成标准 |
| :--- | :--- |
| **1. 代码** | 编译通过；无 `TODO` 空桩；无 `System.out.println`（用 `log`）；符合分层规范 |
| **2. 自测** | 主流程跑通；至少覆盖 3 个边界（空输入 / 超长输入 / 无权限访问） |
| **3. 契约** | 接口字段与 `DEV_SPECIFICATION.md` 一致；Knife4j 上能看到且能调通 |
| **4. 提交** | commit 符合规范；无密钥；无大文件；PR 描述四段完整 |
| **5. 集成** | CI 全绿；合并到 `dev` 后不影响他人功能（合并后 @ 相关成员回归验证） |

**给零编程经验组员的判断口诀**：**能编译 + 能跑通 + 边界不崩 + 说得出改了什么**，四件事全做到了，才叫完成。

## 六、 接口契约治理

### 6.1 契约单一真源

- **唯一真源是 `DEV_SPECIFICATION.md` 第四章**。Postman、Knife4j、前端 TS 类型定义都只是"投影"，与文档冲突时一律以文档为准，并回头修正投影。
- 接口矩阵见 `TEAM_WORK_DIVISION.md` 第三章（**12 个接口**的提供方/调用方）。

### 6.2 契约冻结日

- **第 1 周末（Day 7，Gate 1）为接口契约冻结日**。工期已压缩为 **3 周**，现行排期以 `THREE_WEEK_PLAN.md` 为准；`TEAM_WORK_DIVISION.md` 里的 5 周路线图已作废，其"第 2 周末冻结"的说法不再适用。
- 冻结后，接口字段的任何增删改必须走 **6.3 的变更流程**，不允许"我顺手改一下"。

### 6.3 契约变更四步法（冻结后强制）

1. **提 Issue**：在代码仓新建 Issue，标题 `[契约变更] xxx`，写清改什么、为什么要改、影响谁。
2. **双方确认**：提供方与调用方都在 Issue 里回复同意（这是 C 列咨询的落地点）。
3. **先改文档后改代码**：本仓是 Monorepo，文档与代码同仓——先提一个只改 `DEV_SPECIFICATION.md` 的 PR（标题带 `[契约变更]`），组长合并后，再提改代码的 PR。顺序不能颠倒——否则代码改了文档没改，下一轮 AI Agent 又会按旧文档生成错误代码。
4. **群内通知**：合并后在群里 @ 全体，说明变更点与需要重新拉取的内容。

### 6.4 Mock 先行（解耦依赖，避免"我等你"）

- 成员 B 在接口未实现前，先提供 **Postman Mock 集合或 Knife4j 定义**（路线图第 1 周已安排）。
- 成员 C/D 一律**照 Mock 开发**，不等待后端真实实现；后端实现完成后切换 baseURL 即可。
- Mock 与真实实现的字段必须一致，切换时若发现不一致，按 6.3 走变更流程，而不是前端私自适配。

## 七、 联调节奏与集成窗口

### 7.1 固定集成窗口

| 时间 | 事项 | 参与人 |
| :--- | :--- | :--- |
| 每周三 21:00 | 中期集成：合并各自的 `feature` 到 `dev`，跑一次全链路 | 全体 |
| 每周日 21:00 | 周末集成 + 周报：合并、回归、更新周报与风险状态 | 全体 |
| 第 3 周起 | 每日集成（冲刺期），有问题当天暴露 | 全体 |

**集成窗口的价值**：把"联调冲突"从"最后一晚的灾难"变成"每周 30 分钟的例行公事"。这是企业级协作最重要的节奏设计。

### 7.2 联调依赖顺序

```text
B 建表 + 登录接口  →  C/D 能登录  →  A 的 SSE（依赖 B 的 qa_record/session 持久化方法）
        ↓                                    ↓
   D 课件上传（依赖 A 的切块服务）  →  C 的问答界面（依赖 A 的 SSE + B 的会话接口）
```

- **关键依赖**：A 依赖 B 提供 `saveStreamingRecord` / `createSessionLazy` 两个方法（见 `MEMBER_B_DEV_GUIDE.md` 5.1）。**B 必须在 Day 3 结束前把这两个方法签名给出**（`THREE_WEEK_PLAN.md` 第二节把它标为全项目唯一硬死锁），哪怕内部先返回假数据，否则 A 会被完全阻塞。

### 7.3 阻塞处理

- **阻塞超过 4 小时**：群里 @ 组长 + 在 Issue 打 `blocked` 标签。
- **阻塞超过 8 小时**：组长组织 15 分钟语音会，当场定方案（拆任务 / 换人 / 改方案）。
- **不要硬扛**：零编程经验下，卡住 8 小时通常不是努力不够，而是方向错了。

## 八、 沟通与协作规范

### 8.1 渠道与响应 SLA

| 渠道 | 用途 | 响应时限 |
| :--- | :--- | :--- |
| 微信群 | 只做两件事：**转发关键链接**（PR / 契约变更 / 阻塞上报）与**约会议** | 工作时间 **2 小时内** |
| GitHub Issue | 任务、站会、Bug、契约变更（**一切留痕的事**） | 24 小时内 |
| GitHub PR | 代码评审 | 24 小时内首次响应 |
| 语音会 | 分歧超 24h、阻塞超 8h、每周集成 | 按需，不超过 30 分钟 |

**铁律**：凡是需要"以后还能查到"的结论（需求、契约、决策、Bug 原因），**必须落在 Issue 或 PR 里**，群聊里的结论 24 小时内补录到 Issue。群聊是流水，Issue 是账本。

### 8.2 异步站会（每日，替代晨会）—— 发在 Issue 评论区，不发群里

每人每天开工时，在**当日在做任务的 Issue 评论区**发 3 行（10 秒写完），同时把该卡片在看板上移到对应列：

```text
昨天：完成 PDF 切块，跑通 Chroma 写入
今天：实现 Top-K 检索 + 相似度阈值
阻塞：无 / 阻塞：B 的 qa_record 表还没建好，我先用内存 Map 顶着（已加 blocked 标签）
```

**为什么发 Issue 不发群**：站会记录挂在任务上，组长看板卡的评论列就是全貌，周报直接抄；发群里三天后就找不回来了。微信群只承担两件事：**转发关键链接**（PR / 契约变更 / 阻塞上报，一行链接即可）和**约会议**。

### 8.3 周报模板（每周日，随集成一起）

```text
【周报】第 X 周 成员 A
1. 本周完成：（对照 TEAM_WORK_DIVISION 第 X 周计划，逐条打勾）
2. 与计划的偏差：（提前/滞后？原因？）
3. 下周计划：
4. 风险与需要帮助：
5. 关键决策：（本周拍板了什么，为什么）
```

## 九、 缺陷管理

### 9.1 严重级别与修复时限

| 级别 | 定义 | 修复时限 | 示例 |
| :--- | :--- | :--- | :--- |
| **P0 阻断** | 系统无法启动、演示直接白屏、数据丢失 | **2 小时内** | `dev` 分支编译失败、启动报 `NoSuchBeanDefinition` |
| **P1 严重** | 核心功能不可用，但系统能跑 | **24 小时内** | SSE 不吐字、登录后 403、课件上传后状态卡在 PARSING |
| **P2 一般** | 功能可用但有明显瑕疵 | 本周内 | 样式错位、分页不准、提示文案错误 |
| **P3 优化** | 体验改进 | 排期，可不做 | 动画不流畅、空状态不好看 |

### 9.2 缺陷处理流程

1. 发现者提 Issue（模板 `bug.yml`），**必须写复现步骤**，附截图或报错日志。
2. 组长 24 小时内定级并指派给对应成员。
3. 修复者从 `dev` 拉 `fix/<字母>-<短名>` 分支，PR 描述里写 **根因**（不是"修好了"，而是"为什么会出现"）。**缺陷 PR 不要写 `Closes #`**——写了会在合并时自动关单，跳过第 4 步。
4. 修复后由**发现者**验证并手动关闭 Issue，不是修复者自己关。（任务类 Issue 走 `Closes #` 自动关单，缺陷类走发现者确认关单，两套规则各管各的。）

> **根因要求**：本项目明确要求根因分析（root-cause），不接受"重启一下好了""换种写法就好了"这类表面修复。修完要能回答"为什么之前会错"。

## 十、 风险登记册（Risk Register）

**用途**：把"担心的事"变成"有预案的事"。组长每周集成时更新一次状态列。

| ID | 风险 | 概率 | 影响 | 预警信号 | 应对预案 | 责任人 | 状态 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
